## 🔴 严重问题（5 项）

### S-01 [设计矛盾] F-01 格式优先级与 F-07 识别优先级冲突，架空存储模型

**涉及条款**: F-01、F-07、4.3 数据表

**问题描述**:

F-01 规定："需明确格式处理优先级：**纯文本 > HTML > RTF > 图片**，多格式共存时按优先级选取最高格式存储。"

F-07 规定："若剪切板同时包含多种格式，按'文本 > 图片 > 文件路径'优先级显示内容" 以及 "图片二进制数据存入 content_blob 字段"。

两个优先级体系维度不同（F-01 是**存储格式**优先级，F-07 是**显示类型**优先级），但它们的交互导致了一个自相矛盾的结果：

- 当剪贴板同时包含文本和图片时（最常见的 Office/浏览器复制场景），F-01 的存储优先级会**只存储文本**，丢弃图片。`content_blob` 永远为空。
- 这意味着 F-07 的"图片"类型识别和 F-14 的"图片预览"在实际场景中几乎**不可能触发**——只有用户复制纯图片（无文本格式）时才会出现图片类型的记录。
- 存储模型设计中存在 `content_blob` 和 `content_type = 'image'` 分支，但 F-01 的优先级规则使这些分支成为死逻辑。

**建议**:
- 方案 A：调整 F-01 存储策略为"多格式共存时**保留最高优先级的两种格式**（文本 + 图片备份）"，确保图片预览功能可用。
- 方案 B：将 F-07 的类型识别改为"显示时的覆盖规则"，明确说明存储和显示是两套不同的处理管道，并在数据表中新增冗余标记字段（如 `display_type`）消除歧义。
- 方案 C：如产品侧确认确实不需要图片预览场景的回退（即确实只存文本），则应从 F-07/F-14 中移除图片相关的冗余描述，或者将 F-14 标记为"仅在纯图片复制场景下生效"。

### S-02 [冗余] F-02 与 F-10 职责分离不彻底，仍有"数量管理"的隐性关联

**涉及条款**: F-02、F-10

**问题描述**:

v3 变更摘要声称已修复"F-02 与 F-10 职责分离"（变更项 #2），F-02 回归"仅描述持久化存储职责"，F-10 承担数量限制职责。但仔细阅读发现：

F-02 描述中"所有记录保存到本地 SQLite 数据库，程序重启后不丢失。仅描述持久化存储职责；数量限制相关配置参见 F-10。"——末尾的"参见 F-10"本质上仍在暗示实现者需要同时理解两个功能才能正确实现。F-02 如果没有数量限制的上文，其"持久化存储"的具体含义（存多少？存满了怎么办？）就不完整。

更深层的问题是：**持久化存储** 和 **数量限制与自动清理** 在数据库实现层面是无法彻底分离的——过期淘汰逻辑必然嵌入到 DAO 层的写入逻辑中。强行分离功能描述反而导致实现者需要跨功能拼接完整图景。

**建议**:
- 方案 A：接受二者在实现上的耦合，在 F-02 中简要提及"存储受 F-10 数量限制策略管理"作为前置依赖说明，而非"参见"。
- 方案 B：将 F-02 改为纯数据层描述（表结构、连接管理），将 F-10 作为"存储策略"整体包含持久化与淘汰逻辑。

### S-03 [设计缺陷] 技术选型二元方案导致目录结构与需求描述深度不足

**涉及条款**: 4.1 技术选型、4.2 目录结构

**问题描述**:

文档在 Rust 和 C# 两种技术栈间保持开放，但后续章节**没有保持中立**：
- 4.2 目录结构直接使用了 `Cargo.toml`、`src/main.rs`、`src/` 下的 Rust 模块化结构。如果最终选择 C# (WPF)，这个目录结构需要推倒重来（WPF 项目通常是 `App.xaml`、`MainWindow.xaml`、`ViewModels/`、`Views/` 等）。
- 4.1 推荐方案为"Rust + egui + SQLite + tray-icon"，但对 C# 方案没有给出同等深度的推荐组合。
- 文档深度介于"语言无关的需求"和"Rust 实现方案"之间，导致无论选哪种技术，均有一半的设计细节是无效的。

**影响**: 如果开发团队选择 C#，则 4.2 节的模块划分完全不可用，实现者需要自行设计 C# 项目结构，导致架构一致性下降。

**建议**:
- **明确技术选型决策**后再进入详细设计阶段，或
- 保持两套独立的目录结构设计（Rust 版和 C# 版），标注各自适用场景。

### S-04 [设计矛盾] NF-03 与 NF-04 关于 10,000 条记录的指标存在矛盾

**涉及条款**: NF-03、NF-04、F-10

**问题描述**:

| 条款 | 内容 | 隐含承诺 |
|------|------|---------|
| NF-03 | "10,000 条为设计上限指标……超出上限部分的加载时间不在 NF-03 保证范围内" | 10,000 条以内性能达标 |
| NF-03 | "② 10,000 条记录下首次从数据库加载完成 ≤500ms" | 10,000 条是测试基线 |
| NF-04 | "支持至少 10,000 条文本记录" | 10,000 条是设计的下限承诺 |
| F-10 | "默认值 5000 条，用户可设为 0 禁用限制" | 用户可以关闭上限，无保护 |

这四个条款之间的张力：
- NF-04 说"至少"10,000 条（暗示可以更多），NF-03 说 10,000 条是"上限"，超出不保证性能——"至少"和"上限"互相矛盾。
- 如果用户按照 F-10 将限制设为 0（禁用），数据库可能积累数十万条记录，而 NF-03 只保证到 10,000 条——此时程序行为没有定义。

**建议**:
- 统一术语：将 NF-04 改为"存储上限 ≥ 10,000 条"，NF-03 改为"10,000 条为性能保证上限"。
- 补充 F-10 中"禁用限制"场景下的性能预期说明：指明 10,000 条以上系统不会崩溃但性能会逐步下降。

### S-05 [冗余] NF-06 与 F-18 完全重复定义

**涉及条款**: NF-06（第④点）、F-18

**问题描述**:

NF-06 安全性需求第④点："通过代码审查确保无隐藏网络调用依赖（参见 F-18）"。
F-18 安全性验证："程序编译时通过代码审查确保无隐藏网络调用依赖。审查范围：所有依赖库的网络能力声明、项目代码中的网络 API 调用……审查结果记录在构建流程中。"

**二者内容完全一致**，只是 NF-06 增加了"参见 F-18"的引用。本质上同一个需求被拆成了"非功能需求"中的一个子项和一个独立的"功能需求"。这不符合单一责任原则，也容易导致后续修订时只更新了一个地方而另一个不同步。

**建议**:
- **删除 F-18**，将其内容完整合并到 NF-06 中，作为 NF-06 的一个子条款。
- 或保留 F-18 为"实施策略"（how），NF-06 只描述"安全目标"（what），但当前二者都在描述 what+how，没有层次区分。

## 🟡 一般问题（6 项）

### M-01 [设计缺陷] F-10 设置值为 0 表示"禁用限制"违反用户直觉

**涉及条款**: F-10

**问题描述**:

F-10 规定"用户可设为 0 以禁用限制，此时所有记录永久保留"。这是文档的一个设计决策，但存在 UX 风险：
- 通用直觉：设置为 0 意味着"不保存"或"清空"（如保留条数 = 0 条），而非"无限保留"。
- 常见的剪切板工具（如 Ditto）中，0 通常表示"不限"，但有明确的 UI 文案辅助说明。需求文档中未要求设置界面对此做特殊说明。

**建议**:
- 改为使用 -1 或特殊值（如"无限制"复选框 + 数字输入框联动）代替纯数字 0。
- 如果坚持使用 0，必须在设置界面添加明确的说明文案（如"设为 0 表示不限制保存数量"）。

### M-02 [设计缺陷] F-07 文件路径检测规则过于简单，易误判

**涉及条款**: F-07

**问题描述**:

F-07 描述类型检测规则为："文本内容以盘符路径（如 `C:\`、`D:\`）或 UNC 路径（`\\`）开头 → 标记为'文件路径'。"

这个简单的字符串前缀匹配在以下场景会误判：
- 用户复制了以 `C:\` 开头的代码注释或日志输出（如 `C:\Users\...` 出现在错误信息中）
- 用户复制 SQL 语句中的 `C:\path` 字符串
- 用户复制 Markdown 中的 Windows 路径

没有提供"路径是否为真实存在的文件/目录"的校验逻辑，也没有"路径+文件存在性验证"的兜底策略。

**建议**:
- 增加二次验证：对匹配路径模式的内容，调用 `Path::exists()` 或 `GetFileAttributesW` 验证路径是否真实存在。仅在路径实际存在时才标记为"文件路径"类型，否则按普通文本处理。
- 或降低判断标准：仅标记为"可能为文件路径"（在 UI 中显示特殊图标但带问号标记）。

### M-03 [设计缺失] 数据表缺少 B-tree 索引设计

**涉及条款**: 4.3 数据表结构

**问题描述**:

4.3 节定义了 FTS5 全文搜索索引，但缺少对常规查询路径的 B-tree 索引设计：

| 查询场景 | 涉及列 | 需要索引 | 当前状态 |
|---------|--------|---------|---------|
| 列表按时间倒序 | `created_at` | ✅ | ❌ 无索引 |
| 收藏过滤 | `is_favorite` | ✅ | ❌ 无索引 |
| 来源应用搜索 | `source_app` | ✅ | ❌ 无索引 |
| 去重检查 | `content_hash` | ✅ | ✅ UNIQUE 约束已隐含索引 |

虽然 10,000 条数据量下全表扫描可能依然可接受，但 `created_at DESC LIMIT 50` 这类高频查询缺少索引可能导致 NF-03 的 500ms 加载指标无法满足。

**建议**:
- 在数据表设计中补充明确的索引声明：

```sql
CREATE INDEX idx_clip_records_created_at ON clip_records(created_at DESC);
CREATE INDEX idx_clip_records_is_favorite ON clip_records(is_favorite);
CREATE INDEX idx_clip_records_source_app ON clip_records(source_app);
```

### M-05 [设计缺失] F-17 忽略应用列表缺少性能考量

**涉及条款**: F-17

**问题描述**:

F-17 支持三种匹配方式：窗口标题通配符、进程名、完整路径。每次剪贴板变更都需要进行匹配检查，但：
- 三种匹配方式的**优先级/短路逻辑**未定义（如果进程名匹配了，是否还需要检查窗口标题？）
- 匹配规则的**数量上限**未定义（用户配置了 100 个忽略应用时，每次复制都要做 100 次匹配检查，可能影响响应性能）
- **匹配更新的实时性**未定义（用户添加/删除忽略应用后，匹配规则是否需要重新加载？缓存策略是什么？）

这些缺失的设计细节可能导致在高频复制场景下出现性能问题（与 NF-03 的 200ms 面板响应指标冲突）。

**建议**:
- 补充匹配策略的优先级：进程名匹配 → 完整路径匹配 → 窗口标题匹配（按精确度从高到低，可短路）。
- 设置合理的规则数量上限（如 50 条）或确保匹配算法在 100 条规则下仍能在 1ms 内完成。
- 定义规则更新的缓存刷新策略。

### M-06 [设计缺陷] F-04 交互模式命名易导致用户混淆

**涉及条款**: F-04

**问题描述**:

F-04 定义了两种交互模式：
- **单击模式（默认）**：单击 → 复制 + 自动粘贴 + 隐藏面板
- **双击模式**：单击（仅复制，不粘贴）→ 双击/回车 → 复制 + 自动粘贴 + 隐藏面板

命名问题：
- "单击模式"和"双击模式"字面上描述的是用户操作方式（click vs double-click），但实际区别是"自动粘贴 vs 手动确认粘贴"。
- 用户看到"双击模式"的直觉是"所有操作都需要双击"，但实际上单击仍然做了"复制"操作，只是不自动粘贴。
- 这种命名与行为的不一致会导致用户在切换模式时感到困惑，增加支持成本。

**建议**:
- 采用**以行为命名的模式**：如"自动粘贴模式" vs "手动粘贴模式"（或"确认后粘贴模式"）。
- 或保留交互描述但增加副标题说明，如"单击模式（自动粘贴）" / "双击模式（确认后粘贴）"。

### m-06 [设计缺失] F-01 写回跳过机制在多线程环境下的可见性未定义

**涉及条款**: F-01

**问题描述**:

F-01 推荐"使用内存标记（标志位）而非实际暂停监听器"，并建议在 Rust 实现中可能采用 `AtomicBool`。但需求文档未定义：
- 标记位在不同线程间的内存可见性语义（Relaxed / Acquire-Release / SeqCst）
- 标记位的生命周期（是全局静态变量还是模块级变量）
- 如果写回操作异常中断（panic/异常），标记位是否会泄漏导致后续剪贴板变更被跳过

这些是"推荐做法"下的典型陷阱，需求文档虽然不需要深入实现细节，但应提示这些边界情况。

**建议**:
- 在 F-01 的"写回跳过机制"段落末尾添加一条备注："使用内存标记时需注意异常安全：写回过程中若发生异常，应确保标记位在 finally/Defer 块中被正确清除，防止标记泄漏导致后续监听失效。"
