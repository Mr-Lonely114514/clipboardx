# Windows 全局剪切板管理器 —— 审议报告 v2

> **审议对象**: `需求/需求_v2.md`  
> **审议日期**: 2025-01  
> **严重等级说明**: 
> - 🔴 **严重**: 导致功能冲突、数据不一致或无法实现，必须修正
> - 🟡 **一般**: 影响功能完整性或易用性，建议修正
> - 🟢 **轻微**: 不影响功能，但影响可读性/一致性，可选修正

## 🔴 严重问题

### S-01: F-04 单击行为描述自相矛盾

**位置**: 2.1 节 F-04，第 45 行

**问题描述**: 
同一段描述中存在两套矛盾的交互定义：
- 前半句："点击任意条目时的行为：①...②...③恢复焦点到原活动窗口；④模拟 `Ctrl+V` 自动粘贴"——**单击即自动粘贴**。
- 最后一句："支持交互模式设置：**单击复制到剪切板（不自动粘贴），双击/回车触发自动粘贴**"——**单击不粘贴，双击才粘贴**。

两段逻辑互斥，实现者无法判断默认行为是什么。

**建议修复**: 统一为一种默认行为，并将另一种作为可配置模式。推荐：
- 默认行为：**单击复制到剪切板（不自动粘贴）**，用户按回车或双击触发自动粘贴。
- 删除前半句中"模拟 Ctrl+V 自动粘贴"的硬编码描述，改为引用交互模式配置。

### S-02: F-02 与 F-10 功能完全重复

**位置**: 2.1 节 F-02（第 43 行）与 2.2 节 F-10（第 56 行）

**问题描述**:
两个功能描述核心内容几乎完全一致：

| 要素 | F-02 | F-10 |
|------|------|------|
| 默认保留条数 | 5000 条 | 5000 条 |
| 可关闭限制 | 设为 0 即不限制 | 设为 0 以禁用限制 |
| 超出后行为 | 自动淘汰最旧记录 | 自动淘汰最旧记录 |
| 优先级 | P0 | P1 |

F-02（核心功能）已完整包含 F-10（增强功能）的全部描述。F-10 作为独立功能项存在没有任何新增语义。

**建议修复**: 
方案 A：删除 F-10 条目，将 F-02 描述中的"用户可在设置中关闭此限制"改为更完整的"用户可在设置中调整最大保留条数（默认 5000，设为 0 表示不限制）"。
方案 B：如果希望将"可配置保留条数"作为独立功能条目，则 F-02 应只写"持久化存储"而不涉及数量限制，数量限制全部放到 F-10。

### S-03: `source` 字段 `app_writeback` 与写回跳过机制逻辑矛盾

**位置**: 4.3 节数据表 `source` 字段说明（第 176 行）

**问题描述**:
`source` 字段定义了三个枚举值：`local_clipboard` / `app_writeback` / `cloud_sync`。
其中 `app_writeback` 的含义是"程序写回"，但：
1. F-01 写回跳过机制的目的正是**阻止程序自身写回的内容被监听到并保存**。
2. 既然写回已被跳过/忽略，就不可能产生 `source = app_writeback` 的记录。
3. 这个枚举值在代码中永远不会被写入，属于"死逻辑"。

**建议修复**: 
删除 `source` 字段中的 `app_writeback` 枚举值。如果确实需要审计追踪写回行为，应改为在内存中记录（不持久化到数据库），或在表中增加独立的 `writeback_count` 计数器字段。

## 🟡 一般问题

### M-01: NF-06 审计日志功能无对应功能需求定义

**位置**: 3 节 NF-06（第 81 行）

**问题描述**:
NF-06 要求"内置审计日志记录所有对外网络访问尝试，用户可在设置中查看"，但这个完整的 UI + 存储 + 审计功能没有一个对应的 F-xx 功能需求来描述：
- 审计日志的 UI 入口在哪里？
- 审计日志的存储方式（内存？文件？数据库表？）？
- 审计日志的保留策略？
- 这是一个 P0/P1/P2 功能？

非功能需求（NF）应描述**质量属性**（性能、安全指标），不应隐式定义**功能需求**。审计日志是一个完整的功能模块。

**建议修复**: 
方案 A：新增一个 F-18 功能需求描述审计日志功能，NF-06 改为引用该功能。
方案 B：将 NF-06 的审计日志要求降低为"代码审查确保无隐藏网络调用依赖"，删除审计日志功能要求。

### M-02: F-07 file 类型内容存储字段不明确

**位置**: 4.3 节数据表 `content_text` 和 `content_blob` 字段（第 173-174 行）

**问题描述**:
- `content_text` 说明："text 类型时存储"
- `content_blob` 说明："image 等类型时存储"

当 `content_type = 'file'`（文件路径）时，应该存到哪个字段？文档未明确。
- 文件路径本质是文本（如 `C:\Users\...\file.txt`），应存到 `content_text`？
- 还是文件路径有特殊处理，需要存到 `content_blob`？

不同实现者会做出不同选择，导致数据不一致。

**建议修复**: 
在 `content_text` 字段的说明中补充："text / file 类型时存储文本内容或文件路径"。
或在 `content_type` 的说明中明确 file 类型时内容存在哪个字段。

### M-03: F-09 FTS5 对非文本内容搜索无方案

**位置**: 2.2 节 F-09（第 55 行）

**问题描述**:
F-09 要求"联合搜索 content_text + source_app，FTS5 模糊匹配"，但：
- 图片类型（content_type = 'image'）的记录，`content_text` 为空，`content_blob` 存的是二进制图片数据。
- FTS5 只能索引文本列，无法索引 BLOB 列。
- 当用户在搜索框输入关键词时，图片条目应当被过滤掉还是始终显示？文档未说明。

**建议修复**: 
明确非文本内容的搜索行为：图片/二进制条目在搜索时是否匹配？如果匹配，基于什么字段匹配（如文件名、来源应用）？建议补充："图片和二进制类型的记录在搜索时仅匹配 `source_app` 字段，不匹配内容本身。"

### M-04: F-17 "白名单"命名反向，逻辑反直觉

**位置**: 2.2 节 F-17（第 58 行）

**问题描述**:
原文："允许用户设置'忽略应用'白名单/黑名单，在**白名单**中的应用内的复制操作**不被**记录。"

业界惯例：
- **白名单** = 仅允许列表内的内容 → 列表内的应用**被**记录
- **黑名单** = 禁止列表内的内容 → 列表内的应用**不被**记录

但这里的"白名单"行为实际上是黑名单语义。如果同时提供白名单和黑名单两种模式，这会导致用户严重混淆。

**建议修复**: 
改为明确的两模式配置：
- **排除模式/黑名单**（默认）：添加到列表的应用不记录，其余全部记录。
- **仅记录模式/白名单**：仅记录添加到列表的应用，其余不记录。
或者直接将功能更名为"忽略应用列表"，避免使用"白名单"一词。

### M-05: F-04 交互模式默认值未定义

**位置**: 2.1 节 F-04（第 45 行）

**问题描述**:
"支持交互模式设置：单击复制到剪切板（不自动粘贴），双击/回车触发自动粘贴。"

文档没有指定**默认值**是哪种模式。用户首次使用时：
- 单击是复制还是复制+粘贴？
- 如果用户不知道可以配置，默认行为是什么？

缺少默认值意味着实现者需要猜测，不同实现可能产生不同结果。

**建议修复**: 
明确标注默认交互模式，建议："默认模式：单击复制到剪切板（不自动粘贴），双击/回车触发自动粘贴。"

### M-06: 写回监听器暂停/恢复的生命周期范围不明确

**位置**: 5.1 节 4a 流程（第 218-220 行）

**问题描述**:
流程描述为"暂停剪切板监听器 → 将该记录写入系统剪切板 → 恢复监听器 → 隐藏面板 → 恢复焦点...".

监听器的暂停和恢复仅应覆盖"写入剪切板"这个原子操作，但按照流程图：
- 恢复监听器在步骤4（隐藏面板之前）
- 但实际上监听器恢复后到隐藏面板之间有时间窗口

如果 `SetClipboardData` 本身就会触发 `WM_CLIPBOARDUPDATE` 回调（同步触发），那么在 `SetClipboardData` 返回前监听器已经被触发了，暂停可能来不及。如果 `WM_CLIPBOARDUPDATE` 是异步的（posted message），则恢复监听器到隐藏面板之间的时间窗口可能产生误捕获。

**建议修复**: 
明确监听器暂停/恢复的粒度。推荐两种方案之一：
1. **暂停-写入-恢复** 包裹 `SetClipboardData` 单一调用，确保写入期间监听器不响应。
2. **内存标记法**：设置 `skip_writeback = true` 标记，写入后清除标记，监听器检测到标记则跳过本次变更。不需要暂停/恢复监听器本身。

### M-07: NF-03 10,000 条首次加载 ≤500ms 与 F-02 默认 5000 条矛盾感知

**位置**: 3 节 NF-03（第 78 行）

**问题描述**:
NF-03 要求"10,000 条记录下首次从数据库加载完成 ≤500ms"，但 F-02 默认限制 5000 条，用户需主动关闭限制才可能积累到 10,000 条。

这不是一个严重矛盾，但存在设计上的不一致：性能指标按 10,000 条设计，但默认配置只能存 5,000 条。如果用户关闭限制，是否仍保证 10,000 条的性能？超过 10,000 条时的性能退化曲线是线性的还是指数级的？

**建议修复**: 
在 NF-03 中补充："存储超过 10,000 条时性能会逐渐下降，建议用户根据实际硬件调整存储上限。" 或补充性能退化模型说明。

## 🟢 轻微问题

### N-01: NF-04 与 F-02/F-10 存储数量指标不一致

**位置**: NF-04（第 79 行）"至少 10,000 条" vs F-02/F-10 "默认 5000 条"

**问题描述**: 
NF-04 要求"支持至少 10,000 条文本记录"，F-02 和 F-10 都说默认保留 5000 条。读者可能困惑：到底上限是多少？10,000 是技术上限还是推荐上限？

虽然可理解为 NF-04 是系统能力指标，F-02/F-10 是用户默认配置，但建议统一表述，避免歧义。

**建议修复**: 
将 NF-04 改为"存储容量：支持存储至少 10,000 条文本记录（受用户配置限制，默认上限 5,000 条）"。

### N-03: NF-01 启动速度指标过于宽松

**位置**: 3 节 NF-01（第 76 行）

**问题描述**: 
指标要求"程序启动到托盘驻留 ≤ 1 秒"。对于 Rust 编写的轻量应用（读取配置 → 初始化 SQLite → 注册热键 → 创建托盘），1 秒是一个非常宽松的指标。通常 200-300ms 即可完成，1 秒意味着可能有性能问题但被指标掩盖。

**建议修复**: 
收紧指标至 ≤500ms，或拆分为冷启动/热启动分别定义。

---

### N-04: 5.1 流程图 4b"双击某条记录"说明冗余

**位置**: 5.1 节 4b（第 225 行）

**问题描述**: 
4b 描述为"双击某条记录 → 同 4a（与单击行为相同，具体由用户配置决定）"。

如果单击和双击的行为由配置决定，则双击可以是与单击不同的行为（默认建议：双击自动粘贴）。但这里写的"同 4a"意味着双击行为完全等同于单击，这与"由用户配置决定"矛盾。这条目在文档中制造了混淆。

**建议修复**: 
删除 4b 条目，改为在 F-04 的交互模式说明中统一描述。或改为："4b. 用户双击某条记录 → 根据交互模式配置：若模式为'单击复制，双击粘贴'，则执行自动粘贴流程（同 4a 第①-④步）；若模式为'单击即粘贴'，则双击效果与单击相同。"

### N-05: F-06 托盘左键行为与 F-04 面板点击行为可能混淆

**位置**: F-06（第 47 行）

**问题描述**: 
F-06 说"支持托盘图标左键单击直接弹出面板"，F-04 说面板内单击粘贴。用户需要区分：
- 在托盘图标上左键 → 弹出面板
- 在面板内单击一条记录 → 复制/粘贴

这是两个不同的单击场景，技术上不会混淆，但 UX 文档中应明确说明这种"两段式"交互层次，避免新手用户在文档阅读时产生困惑。

**建议修复**: 
在 F-06 描述中增加说明："托盘图标单击与面板内单击是正交的两层交互：前者唤出面板，后者操作记录。"或在交互流程 5.1 的步骤 0 中补充"0. 用户左键单击托盘图标 → 面板弹出"作为全局入口。
