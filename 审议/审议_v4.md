> **审议性质**: 设计审查
> **严重等级**: 🔴 严重(2) | 🟡 一般(7) | 🟢 轻微(4)

## 🔴 严重问题

### S-01 [设计矛盾] F-01 图片存储与 NF-02 内存指标不可兼得

**位置**: F-01 (L43) + NF-02 (L79)

**问题描述**:
F-01 策略要求"多格式共存时保留最高优先级的两种格式（纯文本 + 图片）"，即**默认开启图片存储**（属于 P0 核心功能）。而 NF-02 规定空闲内存 ≤ 30 MB，且说明"图片功能开启后内存限制单独评估"。

这里存在根本性矛盾：F-01 的图片存储是 P0 核心功能，不是"可选功能"，但 NF-02 的"图片功能开启"指的是 P2 的 F-14（图片预览）。结果是：

- F-01 (P0) 强制存储图片 BLOB → content_blob 持续增长 → 内存占用随记录数线性上升
- NF-02 (P0) 要求 30MB 上限 → 在默认 5000 条记录下，若每条附带几十 KB 图片数据，内存可能轻松突破 30MB
- NF-02 的"图片功能开启后单独评估"与 F-01 的"默认存图"不是同一个开关

**建议**:
- 方案A：NF-02 增加说明"F-01 图片存储功能开启时，内存限制调整为 ≤ 80 MB（以 100 条记录的图片缓存为基准）"
- 方案B：F-01 拆分为两档——纯文本模式下仅存文本（30MB 可达），图片存储作为独立开关（与 F-14 联动）
- 方案C：明确 content_blob 在面板中不全部加载到内存，仅惰性加载当前可见项的预览图

**影响范围**: 直接影响技术选型（Rust 30MB 可达性论证）和架构设计

---

### S-02 [设计遗漏] 多格式共存时 content_type 取值规则未定义

**位置**: F-01 (L43) + F-07 (L54) + 4.3 数据表 (L170-181)

**问题描述**:
F-01 在多格式共存时保留"纯文本 + 图片"两种格式。此时**一条记录同时包含文本数据（content_text）和图片数据（content_blob）**，但 `content_type` 字段取值规则文档未定义：

- 应设为 `'text'` 还是 `'image'`？
- F-07 的显示优先级说"文本 > 图片 > 文件路径"，但这是显示层逻辑还是存储层逻辑？
- 若设为 `'text'`，则类型图标显示为文本，用户可能不知道这条记录还关联了图片
- 若设为 `'image'`，则 F-09 搜索逻辑中"图片类型记录（content_text 为空）不参与搜索"的前提假设在多格式场景下被打破（content_text 非空）

F-09 明确说"对于图片类型记录（content_text 为空），搜索不匹配任何关键词"，这个假设在多格式场景下不成立。

**建议**:
- 新增规则：多格式共存时 `content_type` 统一设为 `'text'`（因为 F-01 策略保证纯文本一定存在）
- 或者新增复合类型值 `'text_with_image'`
- 同时在 F-09 中修正"图片类型记录 content_text 为空"的不准确表述

**影响范围**: F-07 类型识别、F-09 搜索过滤、面板 UI 类型图标展示、数据库查询逻辑

## 🟡 一般问题

### M-01 [逻辑漏洞] "确认后粘贴模式"单击写回缺少跳过机制

**位置**: 5.1 流程图 4a' (L229-231)

**问题描述**:
在"确认后粘贴模式"下，流程图 4a' 描述用户单击某条记录时"将该记录写入系统剪切板（不隐藏面板，不自动粘贴）"，但**未调用写回跳过机制**。而 4b（双击/回车）流程中明确标注了写回跳过机制。

这意味着在确认后粘贴模式下，单击记录触发的写回操作会触发监听器重新捕获该内容。虽然 content_hash UNIQUE 约束可以阻止重复插入（insert 失败），但：
1. 产生了不必要的数据库写入尝试（浪费 CPU）
2. 如果代码未正确处理 UNIQUE 冲突（缺 ON CONFLICT IGNORE），可能导致错误
3. 与 F-01"跳过自触发"的设计意图不一致

**建议**:
在 4a' 流程中补充"写回跳过机制（参见 F-01）"，与 4a/4b 保持一致。

---

### M-02 [场景遗漏] "确认后粘贴模式"下焦点窗口切换问题

**位置**: 5.1 流程图 4a'/4b (L229-238)

**问题描述**:
在"确认后粘贴模式"下，用户单击记录后内容已写入系统剪切板，但面板保持显示。此时用户可能切换到其他窗口再返回面板双击确认。流程图中 4b 的"恢复焦点到原活动窗口"中的"原活动窗口"是单击时记录的窗口句柄，但如果用户在面板保持期间切换了目标窗口，粘贴将发生在错误的位置。

**建议**:
- 方案A：双击/回车时重新获取当前前台窗口（而非使用单击时保存的句柄）
- 方案B：在设置或交互模式说明中明确告知用户此行为限制
- 方案C：在确认后粘贴模式下，双击前的单击不再写回剪切板，仅在双击时统一执行写回+粘贴

### M-03 [定义模糊] F-01 "最高优先级的两种格式"表述不精确

**位置**: F-01 (L43)

**问题描述**:
F-01 定义格式优先级为"纯文本 > HTML > RTF > 图片"，并说要"保留最高优先级的两种格式（纯文本 + 图片）"。但"纯文本 + 图片"是**固定组合**而非按优先级动态选取的两种——"图片"在优先级中排最后，按字面理解"最高优先级的两种"应为"纯文本 + HTML"。

实际意图是"固定保留纯文本和图片两种格式"，但表述为"最高优先级的两种"让读者困惑：若剪切板中无纯文本只有 HTML+RTF+图片，按字面应保留 HTML+RTF，但实际需求文档意图似乎是降级保留可用格式。

**建议**:
将"保留最高优先级的两种格式（纯文本 + 图片）"改为"**固定保留纯文本和图片两种格式**（若存在），纯文本存 content_text、图片存 content_blob；若纯文本不存在，仅保留图片；若图片不存在，仅保留纯文本；若两者均不存在，按格式优先级降序保留一种可用格式"。

### M-04 [场景遗漏] 文件复制（CF_HDROP）场景未被覆盖

**位置**: F-07 (L54) + 数据表 (L170-181)

**问题描述**:
F-07 描述文件路径检测规则时，仅考虑"文本内容以盘符路径开头"的场景（用户复制了形如 `C:\path\to\file.txt` 的文本）。但 Windows 文件复制（资源管理器中 Ctrl+C）的实际机制是通过 **CF_HDROP** 格式传递文件路径列表，不会自动以纯文本形式出现在剪切板中。

文档未定义：
1. 如何从 CF_HDROP 格式提取文件路径
2. 提取后是否存入 content_text
3. content_type 此时应设为 'file' 还是 'text'

当前设计只能覆盖"用户复制了一个文件路径文本"的场景，无法覆盖"用户在资源管理器中复制文件"这一更常见的场景。

**建议**:
- 在 F-07 或数据表说明中补充 CF_HDROP 格式的处理规则
- 新增监听逻辑：当检测到 CF_HDROP 格式时，提取文件路径列表（首个文件路径）存入 content_text，content_type 设为 'file'

### M-05 [指标缺失] NF-01 启动速度指标缺少验证手段

**位置**: NF-01 (L78)

**问题描述**:
NF-01 要求"程序启动到托盘驻留 ≤ 1 秒"，但**验证手段一栏为空白**。对比 NF-03（有明确的验证手段"使用高精度计时器在 CI 中编写性能基准测试"）和 NF-06（有验证手段"抓包工具验证"），NF-01 的验证手段缺失。

启动速度受机器性能、杀毒软件、开机自启加载项等多因素影响，若无明确验证手段，该指标在开发过程中容易被忽视或无法验收。

**建议**:
补充验证手段，如："在 CI 环境中运行启动计时测试（从 main() 入口到托盘图标显示），连续 5 次平均耗时 ≤ 1s，单次不超过 1.5s"

### M-06 [耦合风险] F-01 为 P2 功能预留存储字段导致早期冗余

**位置**: F-01 (L43) + 4.3 数据表 content_blob (L176)

**问题描述**:
`content_blob` 字段的首要消费者是 F-14 图片预览（P2），而 F-01（P0）为了给 F-14 预留数据而提前存储图片。如果 F-14 永远不实现（或推迟到后续版本）：
1. `content_blob` 中的图片数据从未被使用，仅占用磁盘和内存
2. F-01 的"保留两种格式"策略就失去了图片方面的业务价值
3. 存储空间的无效占用会影响 NF-04 存储上限指标的达成效率

虽然"面向未来设计"是合理的，但 P0 功能为 P2 功能承担存储成本，存在前期投入过大的风险。

**建议**:
- 方案A：F-01 在 MVP 阶段仅存储纯文本，content_blob 仅在 F-14 实现后再启用（通过特性开关）
- 方案B：文档中明确标注 content_blob 是"为 F-14 预留"以及预留存储的性能影响说明

---

### M-07 [边界模糊] F-10 无限制模式与 NF-04 存储上限的关系未定义

**位置**: F-10 (L57) + NF-04 (L81)

**问题描述**:
F-10 允许用户设为 -1（无限制），此时"所有记录永久保留"。NF-04 规定"存储上限 ≥ 10,000 条"。当用户选择无限制模式时：
- NF-04 的 10,000 条上限不再适用
- 磁盘空间无限增长无预警机制
- 文档未定义无限制模式下的行为边界（如：磁盘空间不足时是否自动降级？是否给出警告？）

F-10 仅说明"需用户自行管理存储空间"，但缺少技术上的安全防护措施。

**建议**:
- 定义无限制模式下的磁盘空间预警阈值（如：数据库文件 > 1GB 时弹出警告）
- 或定义自动降级策略（超过 100,000 条自动切换为 FIFO 淘汰，忽略用户设置）
- 在 NF-04 中补充说明"用户设置为无限制时，NF-04 指标不适用"

## 🟢 轻微问题

### Mi-01 [表述混淆] 5.1 流程图"检测热键是否被占用（首次运行时）"位置不当

**位置**: 5.1 流程图第 2 步 (L213)

**问题描述**:
流程图第 2 步"用户按下全局热键"的响应中标注"检测热键是否被占用（首次运行时）"。将"首次运行时"放在流程图中（每次热键触发路径上）容易被误解为每次按热键都检测"是否是首次运行"。实际上 F-03 的意思是"首次启动时检测一次"。

流程图更适合将此步骤放在系统生命周期（5.2）的启动序列中，而非热键触发响应中。

**建议**:
从 5.1 步骤 2 中移除"检测热键是否被占用"（已包含在 5.2 启动流程中），或在表述上更精确地改为"首次运行时检测热键是否被占用（仅在程序启动时执行一次）"。

---

### Mi-02 [冗余说明] F-01 写回跳过机制同时描述两种方案应主推一种

**位置**: F-01 (L43)

**问题描述**:
F-01 的写回跳过机制同时描述了"暂停监听器"和"内存标记"两种方案，并推荐了内存标记。但在需求文档中同时保留两种方案的描述增加了读者认知负担，且"暂停/恢复"方案在 F-01 末尾又被提及（"推荐使用内存标记（标志位）而非实际暂停监听器"），内容略有重复。

**建议**:
仅保留推荐方案（内存标记）的详细说明，将暂停监听器的备选方案移至脚注或附录，主流程保持简洁。

---

### Mi-03 [文档耦合] F-10 提及设置界面 UI 分组名，过度约束实现

**位置**: F-10 (L57)

**问题描述**:
F-10 末尾提到"配置项位于设置窗口'存储管理'分组中"。需求文档中约束 UI 的"分组名"属于过度设计——分组名称、布局是 UI/UX 设计阶段的产出，不应出现在需求文档中。这限制了 UI 实现的自由度。

**建议**:
改为"配置项位于设置窗口的存储相关分组中"或删除此句。

---

### Mi-04 [路径限制] 4.2 目录结构使用 `Cargo.toml` 但对 C# 方案未做等效描述

**位置**: 4.2 目录结构 (L103-164)

**问题描述**:
目录结构完全基于 Rust 方案（`Cargo.toml`、`src/main.rs` 等），而 4.1 技术选型同时推荐了 Rust 和 C# (WPF) 两种方案。如果最终选择 C#，目录结构（`Cargo.toml` → `*.csproj`、`src/` 中的 Rust 模块划分等）需要全面调整。

4.1 推荐方案标注为"Rust + egui + SQLite"，但 4.2 未标注"本目录结构基于 Rust 方案"，可能误导读者认为这是一个语言无关的通用结构。

**建议**:
在 4.2 标题或说明中标注"基于 Rust 方案"，或为 C# 方案提供备选目录结构示意。
