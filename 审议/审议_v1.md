# 需求文档 v1 审议报告

> **审议对象**: `需求/需求_v1.md`  
> **审议日期**: 2025-01  
> **问题等级**: 🔴 严重 / 🟡 一般 / 🔵 轻微

---

## 🔴 严重问题

### S-01. 写入回触发监听导致无限循环（架构缺陷）

**问题描述**:  
F-01（自动捕获剪切板变更）与 F-04（选中记录写回剪切板）构成**循环依赖**：

1. F-04 将选中记录写入系统剪切板
2. F-01 的监听器检测到剪切板变更
3. 监听器再次将同一内容写入数据库，产生重复记录
4. 用户每粘贴一次，数据库就多一条重复记录

即使有"500ms 防抖去重"，也无法区分"用户正常复制"和"自己写回触发"，防抖仅能缓解同一内容的重复入库，不能解决架构层面的自触发问题。

**建议修复**:  
- 写回剪切板时设置**标记**（如通过自定义剪切板格式或内存变量跳过监听器的本轮处理）
- 或在写回前暂停监听器，写回完成后恢复

---

### S-02. 默认热键 `Win+V` 与 Windows 系统冲突

**问题描述**:  
F-03 建议默认热键为 `Win+V`，但 Windows 10 (1809+) 和 Windows 11 的**系统内置剪切板历史**已占用 `Win+V`。如果同时使用会导致：
- 系统原生的剪切板面板与 ClipBoardX 面板同时弹出
- 用户体验混乱
- 无法注册成功（Win+V 属于系统保留热键）

**建议修复**:  
- 默认热键改为 `Alt+V` 或 `Ctrl+Shift+Insert`（冲突概率更低）
- 首次启动时检测 Win+V 是否已被系统占用

---

### S-03. 面板焦点管理设计矛盾

**问题描述**:  
文档中存在两处矛盾描述：

| 位置 | 描述 |
|------|------|
| 5.1 步骤2 | 面板"置顶、半透明、**带焦点**" |
| 6. 风险-面板焦点管理 | 面板需要"**穿透焦点**到后台窗口" |

同时，F-11（自动粘贴）要求模拟 `Ctrl+V`，但如果面板自身拥有焦点，`Ctrl+V` 只会粘贴到面板自身，而非用户的目标窗口。

**建议修复**:  
- 统一设计：面板弹出时**不夺取焦点**（使用 `WS_EX_NOACTIVATE`），仅置顶显示
- 或采用两步法：面板带焦点供浏览选择 → 选择后隐藏面板 → 恢复焦点到原窗口 → 模拟 Ctrl+V

---

### S-04. 数据表缺少去重与防循环所需字段

**问题描述**:  
`clip_records` 表缺少两个关键字段：

| 缺少字段 | 必要性 |
|---------|--------|
| `content_hash` TEXT UNIQUE | 无法高效实现"500ms 内相同内容只存一次"的去重逻辑 |
| `source` TEXT | 无法区分记录来源（用户手动复制 vs 自动回写 vs 云同步），导致 S-01 问题无法从数据层面解决 |

**建议修复**:  
- 增加 `content_hash`（SHA256 或 MurmurHash），配合 UNIQUE 约束实现去重
- 增加 `source` 字段（枚举值：`local_clipboard / app_writeback / cloud_sync`）

## 🟡 一般问题

### M-01. F-02 与 F-10 默认行为矛盾

**问题描述**:  

| 功能 | 描述 | 隐含策略 |
|------|------|---------|
| F-02 | 记录持久化保存，**不删除则永久保留** | 默认无限制 |
| F-10 | 可设置最大保留条数，**超出自动淘汰最旧** | 默认有限制 |

两份描述的隐含默认策略相悖，用户无法预判程序行为。

**建议修复**:  
- 明确默认值：如"默认保留最近 5000 条，可关闭此限制"
- 或统一为：默认永久保留，可设置上限

---

### M-02. 技术选型推荐与实际可行性不匹配

**问题描述**:  
推荐方案为 **Rust + egui + SQLite + tray-icon**，但：

| 组件 | 问题 |
|------|------|
| **egui** | 不支持原生托盘图标，需依赖 `tray-icon` crate，而 `tray-icon` 在 Windows 上稳定性一般 |
| **egui** | 全局热键需额外 crate（`global-hotkey`），与 egui 的事件循环集成不够原生 |
| **egui** | 对"全局置顶、半透明、焦点穿透"等 Window 特性的支持依赖底层 win32 封装，egui 本身不提供 |
| **Tauri**（备选） | 系统托盘和全局热键支持通过插件实现，但文档提及不足 |

更成熟的方案可能是 **C# WPF/WinUI 3** 或 **Rust + win32 API 原生窗口**。

**建议修复**:  
- 增加备选方案评估：C# WPF + SQLite
- 如选 Rust，明确 egui 在 win32 平台上的限制及应对策略
- 给出原型验证的建议和风险点

---

### M-03. 系统托盘菜单缺少核心功能入口

**问题描述**:  
F-06 提到托盘右键菜单有"退出/设置"，但缺少**展开/隐藏面板**的入口。如果用户忘记或不知道全局热键，就无法通过托盘使用核心功能。

**建议修复**:  
- 托盘菜单必须包含"显示剪切板面板"条目
- 考虑支持托盘图标左键直接弹出面板

---

### M-04. NF-02 30MB 内存约束过于严格

**问题描述**:  
空闲状态下 ≤30MB 的目标在以下场景下可能无法达到：
- 使用 Rust + egui（egui 自身约 10-20MB，但 OpenGL/Vulkan 后端额外占用显存）
- SQLite 缓存页（10,000 条记录 + 索引约 2-5MB，取决于内容长度）
- 图片预览场景下内存占用会更高

**建议修复**:  
- 放宽至 ≤50MB（空闲状态）
- 或明确测量基准：仅限纯文本场景，图片功能开启后内存限制单独说明

---

### M-05. 缺少"忽略应用"白名单的实现设计

**问题描述**:  
第6节风险中提到了"忽略窗口白名单"作为隐私保护措施，但在第2节功能需求中找不到对应的功能定义——这个设计约束完全没有落到需求里。

**建议修复**:  
- 在 P1 或 P2 中增加"应用白名单/黑名单"功能
- 说明配置方式（应用名称匹配、窗口标题匹配、exe 路径匹配）

---

### M-06. 配置管理范围未定义

**问题描述**:  
`config.rs` 提及配置管理，但未明确：哪些是可配项、配置文件格式（JSON/TOML/YAML）、存储位置（%APPDATA% 还是程序目录）、是否支持运行时热加载。

**建议修复**:  
- 新增一个数据字典表，列出所有配置项及其默认值
- 明确配置文件存放路径：`%APPDATA%/ClipBoardX/config.toml`

## 🔵 轻微问题

### m-01. F-05 "记录删除"功能粒度不恰当

F-05 将"单条删除"和"清空全部"合并为一个功能项。操作复杂度差异较大，建议拆分为：
- F-05a 单条删除
- F-05b 清空全部历史（需二次确认）

---

### m-02. F-08 "收藏/置顶"优先级可能偏低

收藏/置顶被放在 P1，但这是提高用户效率的核心功能——类似手机剪切板的高频操作。建议评估是否提升到 P0 或作为 F-04（记录选择）的子功能。

---

### m-03. F-13 "云同步"设计过度复杂

F-13 描述了"登录账号"进行跨设备同步，对于一个轻量级本地工具来说，引入账号系统过于沉重。建议：
- 优先支持 WebDAV 或本地网络共享（无需账号）
- 或使用纯本地加密文件导出/导入作为轻量同步方案

---

### m-04. 数据表缺少索引设计

按时间倒序查询（created_at）和搜索过滤（content_text）均需建立索引，否则 10,000 条以上记录时性能不达标。

**缺少的索引**: `idx_created_at` (created_at DESC), `idx_content_type` (content_type), `idx_is_favorite` (is_favorite)

---

### m-05. F-04 粘贴行为粒度不足

F-04 描述为"点击条目即复制并粘贴到当前窗口"，但用户可能需要：
- **单击** → 仅复制到剪切板（不自动粘贴）
- **双击/回车** → 复制并自动粘贴

建议将两种交互行为分开定义，或提供配置选项。

---

### m-06. 目录结构中的 tests 层级不规范

Rust 项目中，单元测试通常放在 `src/` 内的模块文件中（`#[cfg(test)] mod tests`），而非单独放在顶层 `tests/` 目录。`tests/` 目录适合集成测试。文档中的目录结构将 `clipboard_test.rs` 和 `storage_test.rs` 放在 `tests/` 下，容易混淆单元测试与集成测试。

---

### m-07. "剪切"（Ctrl+X）无需特殊处理

文档中提到"复制/剪切操作"，但 Windows 中 Ctrl+X（剪切）的行为是：删除选中内容 + 将内容放入系统剪切板。从剪切板监听的角度看，它与 Ctrl+C 没有任何区别，不需要特殊处理。建议在文档中说明这一点以避免歧义。

---

### m-08. 文档版本记录作者标注含混

版本记录中作者为"AI"，正式文档中应标注为真实人名或团队名称。

---

### m-09. 未考虑数据库事务保护

文档没有提到数据库写入的事务保护。在"高频率复制"场景或程序突然崩溃时，可能出现部分写入导致数据损坏。建议说明使用 SQLite WAL 模式 + 事务包裹每次写入。

---

### m-10. 缺少富文本格式的处理说明

F-01 提到"监听 Clipboard 变化"但未说明如何处理 RTF/HTML 格式内容。Windows 剪切板可能同时包含多种格式，建议定义优先级：纯文本 > HTML > RTF > 图片。

---

## 总结

| 等级 | 数量 | 主要影响 |
|------|------|---------|
| 🔴 严重 | 4 | 写入回环导致重复数据；热键冲突导致功能不可用；焦点管理矛盾导致自动粘贴失败；数据表缺少关键字段 |
| 🟡 一般 | 6 | 策略矛盾、选型风险、功能遗漏、约束不合理 |
| 🔵 轻微 | 10 | 粒度、优先级、索引、文档细节等可优化点 |

**核心建议**: 优先修复 S-01（写入回环）和 S-03（焦点管理），这两项直接影响核心流程的可行性。
