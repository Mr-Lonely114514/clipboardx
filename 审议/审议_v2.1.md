## 二、针对 v1 原始需求的发现

> 以下发现直接涉及 v1 原始需求是否被 v2 正确继承/满足。

### 🔴 严重

#### S-01（重编号 S-02 → S-04）: v1 NF-02 内存指标被弱化（30MB → 50MB）

**涉及 v1 需求**: NF-02 —— "空闲状态下内存占用 ≤ 30 MB"

**问题描述**:
v2 将内存指标从 30MB 放宽至 50MB（v2 变更摘要第 10 条明确记录）。这是一个原始需求指标的**退化**。

**严重程度分析**:
- 30MB → 50MB 是 67% 的增幅
- 对于 Rust 编写的轻量应用，空闲状态主要是 SQLite 缓存 + UI 框架开销，30MB 是合理指标
- 放宽至 50MB 降低了产品的竞争力（对标 Ditto 等同类产品的轻量特性）

**建议修复**:
1. 回归 v1 的 ≤30MB 指标，或在变更摘要中给出充分的技术理由
2. 如果确需放宽，应在需求文档中标注"变更说明"并在审议中记录

---

#### S-02（原 S-02）: F-02 与 F-10 功能完全重复

**涉及 v1 需求**: F-02（持久化存储）与 F-10（数量限制）

**问题描述**:
v2 将"默认保留 5000 条"写入 F-02 的描述中，导致 F-02 与 F-10 的核心语义完全重叠：

| 要素 | F-02 | F-10 |
|------|------|------|
| 默认保留条数 | 5000 条 | 5000 条 |
| 可关闭限制 | 设为 0 即不限制 | 设为 0 以禁用限制 |
| 超出后行为 | 自动淘汰最旧记录 | 自动淘汰最旧记录 |
| 优先级 | P0 | P1 |

v1 中 F-02 只描述"持久化存储（程序重启后不丢失）"，F-10 描述"可设置最大保留条数"。v2 将应该属于 F-10 的配置细节移入了 F-02，导致冗余。

**建议修复**: 
方案 A：删除 F-10，在 F-02 中完善数量限制描述。
方案 B：F-02 回归 v1 的简洁描述（仅"持久化存储"），数量限制全部归入 F-10。

---

### 🟡 一般

#### M-01（原 M-04）: F-17 "白名单"命名反向，逻辑反直觉

**涉及 v1 需求**: 无直接对应（F-17 是 v2 新增），但影响需求可理解性

**问题描述**:
v2 F-17 "白名单中的应用内的复制操作不被记录"——业界惯例中白名单语义是"仅允许"，此处实际是黑名单语义。

**建议修复**: 
更名为"忽略应用列表"，或明确区分白名单/黑名单两种配置模式。

---

#### M-02（原 M-07）: NF-03 与 F-02 性能指标与默认配置不匹配

**涉及 v1 需求**: NF-04（支持至少 10,000 条）vs v2 F-02（默认 5000 条）

**问题描述**:
v2 NF-03 要求"10,000 条记录下首次加载 ≤500ms"，但默认只存 5,000 条。用户需主动关闭限制才可能达到 10,000 条。负载超过 10,000 条时的性能退化曲线未说明。

**建议修复**: 
补充性能退化模型说明，或在 NF-03 中标注"10,000 条为设计上限，超出后性能可能下降"。

---

### 🟢 轻微

#### N-01（原 N-01）: NF-04 与 F-02/F-10 存储数量指标不一致

**涉及 v1 需求**: NF-04（支持至少 10,000 条）vs F-02（默认 5000 条）

**问题描述**:
同 M-02 但程度更轻。NF-04 是系统能力指标，F-02 是默认配置，二者不矛盾但表述容易引起困惑。

**建议修复**: 
在 NF-04 中补充"受用户配置限制，默认上限 5,000 条"。

## 三、针对 v2 新增内容的设计/实现层面发现

> 以下发现针对 v2 相比 v1 **新增的设计细节、技术方案或规格描述**，不属于原始需求审议的核心范畴，但有助于完善 v2 需求文档的完整性和一致性。标注为 **A（Additional）** 以区分于核心需求发现。

### 🔴 严重设计问题

#### A-01（原 S-01）: F-04 单击行为描述自相矛盾（v2 新增交互模式）

**涉及内容**: v2 F-04 新增的"交互模式设置（单击/双击）"

**问题描述**:
v2 F-04 同一段中存在两套矛盾的交互定义：
- 前半句：单击即自动粘贴
- 最后一句：单击复制到剪切板（不自动粘贴），双击/回车才触发自动粘贴

**归属说明**: 该矛盾存在于 v2 新增的设计文本内部，v1 原始需求行为统一且明确。此问题属于 v2 新增设计的不一致。

**建议修复**: 
统一为一种默认行为。推荐默认：单击复制到剪切板（不自动粘贴），双击/回车触发自动粘贴。

---

#### A-02（原 M-01）: NF-06 审计日志功能无对应功能需求定义

**涉及内容**: v2 NF-06 新增的"内置审计日志"要求

**问题描述**:
v2 NF-06 新增了"内置审计日志记录所有对外网络访问尝试"的要求，但审计日志是一个完整的 UI+存储+审计功能模块，应有对应的 F-xx 功能需求来定义其 UI 入口、存储方式、保留策略等。

**归属说明**: v1 NF-06 仅要求"不收集隐私数据、不发送网络请求"，审计日志是 v2 新增内容。

**建议修复**: 
新增 F-18 功能需求描述审计日志，或将审计日志要求降低为"代码审查确保无隐藏网络调用"。

---

#### A-03（原 S-03）: `source` 字段 `app_writeback` 与写回跳过机制逻辑矛盾

**涉及内容**: v2 数据表新增的 `source` 字段

**问题描述**:
`source` 字段定义了 `app_writeback` 枚举值，但 F-01 写回跳过机制的目的正是阻止程序自身写回被记录，因此 `app_writeback` 永远不会被写入，属于"死逻辑"。

**归属说明**: v1 数据表仅有 `id/content_type/content_text/content_blob/source_app/is_favorite/created_at/updated_at`，没有 `source` 字段。这是 v2 新增数据库设计中的逻辑矛盾。

**建议修复**: 
删除 `app_writeback` 枚举值。如需审计写回行为，使用独立计数器而非数据表字段。

---

### 🟡 一般设计问题

#### A-04（原 M-02）: F-07 file 类型内容存储字段不明确

**涉及内容**: v2 数据表 `content_text` / `content_blob` 字段说明

**问题描述**:
`content_type = 'file'` 时，文件路径应存到哪个字段？文档未明确。

**归属说明**: v1 F-07 仅要求"区分类型、显示图标"，未要求指定存储字段。这是数据库设计层面的说明不完整。

#### A-05（原 M-03）: F-09 FTS5 对非文本内容搜索无方案

**涉及内容**: v2 F-09 新增的 FTS5 技术方案

**问题描述**:
图片类型的记录 `content_text` 为空，FTS5 无法索引 BLOB 列，文档未说明非文本内容的搜索行为。

**归属说明**: v1 F-09 仅要求"实时过滤"，FTS5 是 v2 自选的技术方案。

---

#### A-06（原 M-05）: F-04 交互模式默认值未定义

**涉及内容**: v2 F-04 新增的交互模式配置

**问题描述**:
文档没有指定默认交互模式，实现者需猜测。

**归属说明**: 交互模式是 v2 新增的设计概念，v1 原始需求只有一种确定的单击行为。

---

#### A-07（原 M-06）: 写回监听器暂停/恢复的生命周期范围不明确

**涉及内容**: v2 5.1 节写回流程描述

**问题描述**:
监听器暂停/恢复应覆盖"写入剪切板"这一原子操作，但流程图中恢复时机可能产生误捕获窗口。

**归属说明**: v1 F-01 仅要求"监听变更"和"写回跳过"，不涉及实现方案。这是实现层面的问题。
